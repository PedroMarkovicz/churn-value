# churn-value — Design Specification

Status: **Accepted** · Date: 2026-09-26 · Decisions recorded in [`docs/adr/`](adr/)

## 1. Purpose

A portfolio-grade churn application that answers the question a business actually asks:
**"Which customers should we spend money to retain, how much should we spend, and what is it worth?"**

Predicting churn is the means. The product is a *profit-optimal retention decision* with an honest account of its uncertainty.

The project succeeds if a reviewer can:

1. Open a public URL and, within one minute, see the model's value in money against sensible alternatives.
2. Change business assumptions (incentive, acquisition cost, acceptance rate, margin, budget) and watch the optimal decision update live.
3. Clone the repo, run one command, and reproduce every number shown on the site.

### Origin

This project reuses the *business concepts* of an earlier internal project (not its code or data). Those concepts are:

| Kept (reformulated) | Corrected | Dropped |
|---|---|---|
| Retention cost proportional to customer value: `CRC = λc · V` | "Saldo CAC = saved revenue − ΣCAC" double-counted value → CAC now enters as an *avoided cost* (§4) | Compounded multi-period projection of a one-off gain |
| Acquisition cost as a multiple of retention cost: `CAC = λa · CRC` (λa 5–25, HBR) | 100 % retention success assumed → acceptance rate γ | Fixed 0.5 threshold on class-weighted, uncalibrated scores |
| Charging contact cost to false positives | Revenue treated as value → gross margin | RFM K-means "CLV" category |
| User-configurable business parameters | Random split on a single snapshot → rolling-origin temporal validation | Accuracy as a headline metric |
| Purchase cadence and the *expected next purchase window* | Small test set without uncertainty → cluster-bootstrap CIs | |
| Per-customer drill-down | | |

**No data, identifiers, branding or code from the internal project may enter this repository.**

## 2. Data

**UCI Online Retail II** — Chen, D. (2012), DOI [10.24432/C5CG6D](https://doi.org/10.24432/C5CG6D), CC BY 4.0.
It contains 1,067,371 invoice lines from a UK-based online wholesaler of giftware, covering 2009-12-01 to 2011-12-09, with amounts in £.

- Downloaded by script and verified with SHA-256 (`572e3627…0408e67bfb`, pinned in config). The raw file is not committed. `Description` holds mixed types and is read as `str`.
- Cleaning rules, verified on the real file (1,067,371 → 791,021 lines; 5,872 customers), applied in a fixed order by `CLEANING_RULES` (notebook 02 audits each one):
  - drop 34,335 exact duplicate lines;
  - drop rows without `Customer ID` (22.8 %);
  - drop rows with price ≤ 0;
  - drop invoices prefixed `A` (bad-debt adjustments);
  - drop stock codes that do not start with 5 digits (`POST`, `DOT`, `M`, `C2`, `BANK CHARGES`, gift vouchers…);
  - drop C-invoices with positive quantity, which are inconsistent;
  - drop **same-day reversals**: a sale and its cancellation on the same day for the same customer, product, price and quantity, matched one-to-one. There are 1,571 pairs (3,142 lines, £366k of phantom gross sales, 359 customers). The two largest pairs are orders of 80,995 and 74,215 units cancelled within minutes. Returns on a later day are genuine and are kept. Without this rule, returns would appear to be 4.2 % of gross sales instead of 2.1 %.
- Invoices prefixed `C` (cancellations) enter the features only through `return_rate`. They never count as purchases.
- A *purchase* is a distinct invoice day per customer.

This is a **non-contractual** setting: churn is never observed directly and must be defined (§3).

## 3. Problem formulation

### 3.1 Snapshots

Monthly cutoffs `t`. For each `t`, features use only transactions `≤ t`. The label uses the window `(t, t + H]` with **H = 90 days**. The pipeline is parameterised in H, but the app ships a single horizon.

- Last cutoff with a closed label window: **2011-09-10** (data end 2011-12-09 − 90 d).
- First cutoff: ≥ 6 months of history, **2010-06-10**.
- Result: **16 cutoffs**, generated by offsetting whole months from the last cutoff, which avoids day-of-month drift.
- Measured on the real data: **1,297–2,163 eligible customers per cutoff**, with a churn rate between **24 % and 52 %**. The rate is strongly seasonal and peaks for cutoffs whose window starts after the Christmas season.

### 3.2 Eligible population (cadence-aware)

At cutoff `t`, a customer is eligible if:

1. they have **≥ 2 distinct purchase days** before `t`, so that cadence is defined; and
2. their **expected next purchase** `E = last_purchase + cadence` lies in `[t − f·H, t + H + f·H]`, with **f = 0.5**,

where `cadence = (last − first) / (n_purchase_days − 1)`.

Rationale: this keeps only customers who *should* buy within the horizon, so the absence of a purchase is informative. It removes customers with naturally long cycles, whose "churn" would be trivial, and customers who were already long gone. Single-purchase customers are excluded, which is documented as a limitation.

### 3.3 Label

`churn = 1` ⇔ no purchase in `(t, t + H]`.

### 3.4 Features (computed at `t`)

The **base** features are editable in the what-if view:

- `recency_days`
- `n_purchase_days`
- `tenure_days`
- `total_spend`
- `avg_order_value`
- `n_distinct_products`
- `return_rate`
- `spend_90d` and `spend_prev_90d`
- `purchases_90d`
- `cadence_cv` (dispersion of inter-purchase gaps)
- `bought_same_window_last_year` (purchase in `(t − 365, t − 365 + H]`)
- `is_uk`

The **context** features describe the cutoff rather than the customer: `cutoff_month_sin` and `cutoff_month_cos`. They are fixed in the what-if view. The prototype showed that supervised models need them for calibration to carry across seasons (§5.6).

The **derived** features are recomputed in TS for the what-if view and guarded by golden vectors (§7.3):

- `cadence_days`
- `overdue_ratio = recency / cadence`
- `expected_purchases_H = H / cadence`
- `spend_trend = spend_90d / (spend_prev_90d + ε)`

Derived features are kept **few and arithmetic** by design.

## 4. Economics (the core)

### 4.1 Per-customer quantities

| Symbol | Definition | Source |
|---|---|---|
| `pᵢ` | calibrated churn probability | model |
| `Vᵢ` | value at risk **conditional on staying**: `m · AOVᵢ^GG · (T / cadenceᵢ)` | Gamma-Gamma AOV + cadence |
| `CRCᵢ` | retention incentive `= λc · Vᵢ` | original concept |
| `CACᵢ` | replacement cost `= λa · CRCᵢ` | original concept |
| `Bᵢ` | benefit of preventing the churn `= min(Vᵢ, CACᵢ)` | a rational firm covers a loss the cheapest way |

- `AOVᵢ^GG` is the Gamma-Gamma shrunk average order value. Its closed form is simple, so it can also be recomputed in TS.
- `Vᵢ` is **conditional on the customer staying**. The BG/NBD CLV already discounts by P(alive), and multiplying it by `pᵢ` would count churn risk twice.
- A cadence floor (e.g. 7 days) prevents very small cadences from producing extreme `Vᵢ`.

### 4.2 Expected profit of contacting customer i

```
E[πᵢ] = pᵢ · γ · (Bᵢ − CRCᵢ)  −  (1 − pᵢ) · CRCᵢ  −  c
```

- A churner who accepts the offer (probability γ) yields the avoided loss minus the incentive.
- A non-churner takes the incentive for free.
- Every contact costs `c`.

This follows the EMP framework of Verbraken, Verbeke & Baesens (2013, IEEE TKDE 25(5)), with acquisition cost integrated through `Bᵢ`.

**Why not `Vᵢ + CACᵢ`:** if a lost customer is replaced, the replacement restores ≈ V at cost CAC. If they are not replaced, the loss is V. The two costs are never both incurred.

**Visible consequence:** because `CAC = λa·λc·V`, the ratio CAC/V is λa·λc. With the defaults (λa = 10, λc = 0.10), CAC = V exactly, which is the boundary between the two regimes of B. The UI states which regime applies.

### 4.3 Decision rule (no threshold search on test data)

- **Unconstrained:** contact customer i iff `E[πᵢ] > 0`. With calibrated `pᵢ` this is the Bayes-optimal, per-customer rule. The implied threshold is `p* = (CRC + c) / (γ·(B − CRC) + CRC)`, and it varies per customer.
- **Budget / capacity mode:** rank customers by `E[πᵢ]` and greedily take the top-k until the expected spend `Σ [c + CRCᵢ·(pᵢγ + 1 − pᵢ)]`, or the number of contacts, reaches the limit.

The profit-vs-%-contacted curve is still plotted. The gap between its empirical maximum and the analytic rule is shown as a **calibration diagnostic**.

### 4.4 User-configurable parameters (encoded in the URL)

| Parameter | Default | Range | Note |
|---|---|---|---|
| Gross margin `m` | 0.35 | 0.05–0.80 | dataset has revenue only |
| Retention intensity `λc` | 0.10 | 0–0.50 | original range; see note below |
| Acquisition multiple `λa` | 10 | 1–25 | mid of HBR 5–25× |
| Acceptance rate `γ` | 0.30 | 0–1 | EMP literature prior Beta(6,14), mean 0.3 |
| Contact cost `c` | £1 | £0–20 | |
| Value horizon `T` | 365 d | 90–730 d | `T = H` reproduces the original window-revenue view |
| Budget | off | £ or N contacts | |

**Why not the original defaults (λc = 0.25, λa = 5).** The original charged 25 % of the *90-day revenue*. Applied to a 12-month margin V, the same λc is an incentive almost 4× larger. On the test cutoff, the break-even probability is then ≈ 0.53, and even the best untuned model loses money (the oracle makes £74k). With λc = 0.10 and λa = 10, the oracle makes £88.6k, contacting everyone loses £128k, and an untuned seasonal LightGBM made about +£17k in the prototype. The EMP literature uses an incentive of about 5 % of CLV (Verbraken et al., 2013). The original values remain reachable on the sliders.

`γ` is an **assumption, not an estimate**. The dataset has no treatment or control data, so uplift modelling is impossible. The sensitivity page exists because of this.

### 4.5 Policies compared

The policies compared are: do nothing, contact all, random (same size as the model's policy), cadence rule, BG/NBD, logistic regression, GBDT, and oracle (perfect information).

For each policy the app reports:

- expected profit;
- **realized backtest profit** on the holdout labels, with γ applied in expectation;
- **% of oracle profit captured**.

## 5. Modelling & evaluation

### 5.1 Model ladder

Each rung must justify its complexity in money:

1. **Cadence rule** — score = `overdue_ratio`. This is the unused `Threshold_Churn_Dias` idea from the original project.
2. **BG/NBD P(alive)** — fitted by maximum likelihood with scipy, from the closed-form likelihoods of Fader, Hardie & Lee (2005), with a small L2 penalty on the log-parameters. The Gamma-Gamma model, which gives the AOV used in V, is fitted the same way.
   - PyMC-Marketing is not used because its PyTensor backend needs a C toolchain on Windows.
   - `lifetimes` is archived and is not used either.
   - Parameter-recovery tests on simulated data validate the implementation.
3. **Logistic regression** — standardised features, with splines where warranted.
4. **LightGBM** — tuned with Optuna under temporal CV.

Every model is **calibrated** (isotonic or Platt, chosen on the calibration cutoff).

### 5.2 Temporal validation (leakage-safe)

- **Test (holdout):** cutoff 2011-09-10 (1,918 customers, 30.8 % churn).
- **Calibration:** cutoff 2011-06-10 (1,852 customers, 43.2 % churn). Its label window closes before the test cutoff.
- **Training:** the 10 cutoffs from 2010-06-10 to 2011-03-10, i.e. those with `t + H ≤ 2011-06-10`.
- **Tuning / model selection:** rolling-origin CV inside the training cutoffs. The validation cutoff is `c_k`, and training uses the cutoffs with `t + H ≤ c_k`.

The same customer may appear in many snapshots. Temporal separation of label windows prevents leakage.

### 5.3 Metrics

All metrics carry 95 % CIs from a **customer-clustered bootstrap**.

- Ranking: PR-AUC (primary) and ROC-AUC.
- Calibration: Brier score and a reliability diagram.
- Targeting: lift and gains at k.
- Business: **EMP** (integrated over γ ~ Beta) and profit at the default scenario.

Accuracy is not headlined.

### 5.4 Explainability

- SHAP (TreeExplainer) global importance and per-customer contributions, precomputed.
- The what-if view shows how `p` and `E[π]` change. It does **not** recompute SHAP in the browser.

### 5.5 Stability

Metrics and profit per cutoff, plus drift in key features across snapshots (PSI), give a monitoring view without inventing infrastructure.

### 5.6 Known risks

- **Calibration transfer across seasons is the central risk, and it has been measured.** The baselines rank reasonably well:

  | Model | ROC-AUC | PR-AUC | Mean calibrated p on test (actual 0.31) | Expected vs realized profit |
  |---|---|---|---|---|
  | BG/NBD | 0.71 | 0.50 | 0.49 | expected +£128k, realized −£23.7k |

  The calibrated probabilities do not transfer from the June cutoff to the September cutoff, so the baselines lose money:
  - The score itself drifts between cutoffs, because P(alive) falls as the customer's age T grows.
  - Seasonally matched calibration (Sep-2010) does not fix it.
  - Pooled calibration does not fix it.
  - Saerens et al. (2002) EM prior adjustment makes it worse, because it assumes p(x|y) is stable.

  In an untuned prototype, **LightGBM with the context features** calibrated to a mean of 0.29 against the actual 0.31. It realized about +£17k at the default scenario. The Model page must therefore show **expected vs realized profit side by side**. Calibration on the test cutoff is a first-class result, not a footnote.
- **Two root causes found by the notebooks** (04 and 06):
  - **The eligibility window absorbs the lateness signal.** Inside it, churn stays between 35 % and 42 % whatever the overdue ratio, which is why the cadence-rule baseline barely beats random (ROC-AUC 0.55). The model has to find its signal in frequency and recent activity instead.
  - **The BG/NBD score drifts by construction.** Refitted at each cutoff, its estimated dropout probability grows from ≈ 0 to 6 % per purchase as history accumulates, so the same customer's P(alive) changes between cutoffs for reasons unrelated to their behaviour.
- Small population: a few thousand eligible customers per cutoff.
- The holdout's label window covers the Q4 peak. Seasonality is reported, not hidden.
- Wholesale customer heterogeneity.
- The value of γ is assumed.
- The `CAC = λa·λc·V` coupling is inherited from the original project and made explicit in the UI.

## 6. Architecture

```
churn-value/
├─ ml/          Python package (uv): data · labels · features · models · economics · evaluation · export · cli
│  └─ tests/    unit, leakage (property-based), economics, golden-vector generation
├─ web/         Vite + React + TypeScript SPA
├─ contracts/   JSON Schemas (generated from Pydantic) → generated TS types · golden vectors · feature spec
├─ docs/        design.md · adr/ · model card (generated)
└─ .github/     CI + deploy workflows
```

### 6.1 Static-first + batch

Churn scoring is a batch process: a company scores its base monthly and runs campaigns. A real-time inference API would add infrastructure without a matching need. The design is therefore:

- Python **batch pipeline** → versioned artifacts.
- Static SPA consumes the artifacts. All economics run client-side, so sliders respond instantly and there is no server, no cold start and no hosting cost.
- What-if inference runs in the browser: LightGBM → ONNX via `onnxruntime-web`, with the calibrator exported as a lookup table.

### 6.2 Artifacts (typed contract)

| Artifact | Content |
|---|---|
| `manifest.json` | contract version, git SHA, data SHA-256, config hash, created-at |
| `customers.json` | holdout snapshot: id, `p`, base and derived features, `cadence`, `AOV^GG`, actual label, top SHAP contributions |
| `timelines.json` | per-customer purchase days (lazy-loaded) |
| `evaluation.json` | per-model metrics with CIs, PR/ROC/reliability/lift curves, per-cutoff stability, drift |
| `experiments.json` | summary of MLflow runs (models, params, fold metrics) |
| `feature_spec.json` | feature order, dtypes, valid ranges, base/derived split |
| `model.onnx`, `calibrator.json` | what-if inference |
| `golden/*.json` | test vectors for economics and derived features |

Schemas are generated from Pydantic models, and TS types are generated from the schemas. **A contract change on the Python side breaks the web build.**

### 6.3 Frontend

- Vite + React + TypeScript
- Tailwind + shadcn/ui
- TanStack Table
- Observable Plot or visx for the curves
- Scenario state in the URL, so any scenario is a shareable link
- Vitest (economics parity through golden vectors) and Playwright (e2e smoke)

### 6.4 Pages

1. **Overview** — the problem, the headline result at the default scenario (% of oracle profit captured, model vs cadence rule), and how to read the app.
2. **Retention Simulator** — parameters, profit curve with the optimum, policy comparison, budget mode.
3. **Sensitivity / Break-even** — heatmaps over γ × λc (and λa) showing where the campaign is profitable and the current scenario's safety margin.
4. **Action List** — customers ranked by `E[π]`. A drawer shows `p`, `V`, CRC, CAC, B, `E[π]`, the SHAP waterfall, the **cadence timeline** (purchase history, expected-next-purchase window, horizon H) and the **what-if** editor.
5. **Model** — model ladder with CIs, curves, calibration, SHAP global, per-cutoff stability and drift, experiment summary.
6. **Methodology / Model card** — label and eligibility diagram, validation scheme, assumptions, limitations, data licence.

Out of scope, by decision: CSV upload of new customers (it would require a second feature pipeline in TS), a hosted API, LLM-generated narratives, uplift modelling (no treatment data), and user accounts.

### 6.5 ML engineering

- `uv` + `pyproject.toml`, ruff, pyright, pytest, pre-commit.
- Typer CLI with stages: `download → snapshots → features → train → evaluate → export`.
- YAML config validated by Pydantic; Pandera schemas; fixed seeds.
- **MLflow (local)** tracks runs. `evaluate` exports `experiments.json`, so the site shows the tracking history.
- The model card is generated from the evaluation outputs.

### 6.6 CI/CD

- **On PR:** ruff, pyright, pytest; eslint, tsc, vitest, playwright; contract drift check (regenerated TS types must match); Cloudflare preview deploy.
- **On `main`:** deploy to **Cloudflare Workers (static assets)** via GitHub Actions.

## 6.7 Analysis notebooks (ADR 0012)

**Role.** The notebooks are the project's *reasoning*, not its pipeline.
- The Typer CLI stays the single source of truth for every artifact.
- Each notebook imports the same `churnvalue` functions and reads the CLI's outputs.
- A notebook writes only reports: a summary JSON of every number quoted in its text, plus its figures.
- **No business rule or transformation is defined in a notebook.** If a notebook needs reusable logic, that logic goes into the package, with tests. Descriptive aggregation and plotting may live in the notebook.

**Sequence.** The sequence adapts the classic ingestion → cleaning → EDA → preprocessing → training → evaluation flow to non-contractual churn. It adds a *problem-framing* stage, because the label is constructed rather than given. It also separates statistical evaluation from business value, because the central finding of this project is that a model can rank well and still lose money.

**Design system** (adapted from the author's earlier project; layout reused, accent replaced):
- **Header card** with "CHURN-VALUE · pipeline stage NN", a title and a one-line thesis, followed by a paragraph that links this stage's question to the previous one.
- **Contract table:** Input / Outputs / Parameters / Shared code.
- **A "Pipeline rule" paragraph.**
- **A chip row** of section codes, ending in "✓ hand-off".
- **Section bars** reading "code · title", with a monospace tag on the right.
- **Closing callouts:** "Decision taken here", "Left for a later stage" and, new, "Key finding".
- **Colour:**
  - accent **indigo `#4A3AA7`** for all chrome;
  - churners are the emphasis in red **`#E34948`**, with retained customers as grey context;
  - models use a fixed categorical order (`#2A78D6`, `#EB6834`, `#1BAF7A`, `#EDA100`, `#E87BA4`), validated with the dataviz validator and direct-labelled because of the contrast warnings;
  - profit uses a diverging blue↔red scale with a grey midpoint, and never appears on the same chart as the churn emphasis.
- **Plotting:** a quiet matplotlib style (hairline grid, no top or right spines, left-aligned bold titles), implemented in `churnvalue.viz.style`. Sample sizes are always annotated. There are no dual axes.
- **Outputs:** every number quoted in a notebook's text comes from its `S` dict, written to `reports/results/NN_summary.json`. Figures are saved as `reports/figures/NN_*.png`.

**Execution and publication.**
- `churnvalue notebooks [--only NN]` executes each notebook in place, top to bottom, in the project environment, and fails on the first error. It then exports HTML with the full design to `reports/notebooks/`.
- Executed `.ipynb` files are committed with their outputs. GitHub renders their content but strips the inline styles.
- The styled HTML is published with the web app under `/notebooks/` (Plan 4), and the Methodology page links to it.
- CI lints notebooks with `nbqa ruff` and checks that each committed notebook was executed in order. A manual workflow re-executes them against the real data.

## 7. Testing strategy

1. **Label and eligibility** — hand-computed expectations on small synthetic transaction fixtures.
2. **Leakage (property-based)** — mutating any transaction after `t` must leave all features at `t` unchanged. Temporal folds must never overlap label windows.
3. **Economics parity** — Python generates golden vectors (inputs → `V`, CRC, CAC, B, `E[π]`, decision, budget selection, derived features). Vitest asserts TS equality within tolerance.
4. **ONNX parity** — ONNX and native LightGBM predictions match on the holdout within tolerance.
5. **E2E smoke** — the site loads, a slider changes the optimal policy, and a customer drawer opens.
